## 1. Что должно быть видно

Требования сформулированы как вопросы, на которые нужно отвечать за секунды, а не за запросы в консоли.

| № | Вопрос | Чем отвечаем | Сторона |
|---|---|---|---|
| Н-1 | Какие пакеты пришли на портал | список пакетов с временем, каналом, кодом, числом конвертов | веб |
| Н-2 | Что внутри пакета | тело запроса как есть + разбор по конвертам и замерам | веб |
| Н-3 | Как пакет обработался | по каждому конверту: ok / duplicate / rejected / error + замечания `issue` + длительность | веб |
| Н-4 | Что попало в базу | стенд, поколение, замеры, паспорт, история — что именно записано | веб |
| Н-5 | Какие пакеты сформировались, ушли, не ушли | журнал пакетов и очередь с причинами отказа | 1С |
| Н-6 | Каким каналом шли и в каком он состоянии | пакет → канал, уровень TLS, длительность; состояние каждого канала | обе |

Ключевое требование: **один идентификатор связывает обе стороны** — иначе сверка «что отправил / что приняли» делается глазами по времени.

### 2.3. Что уже связывает стороны частично

- `request_id` генерируется в `handleIngest` **один раз на HTTP-запрос** и попадает в каждую строку `ingest_log` — то есть пакет на вебе уже можно собрать группировкой по `request_id`.
- `handleIngest` **уже принимает** `X-Request-Id` от клиента и подставляет свой, только если заголовка нет (`internal/web/ingest.go:68-71`). Значит корреляция на стороне веба почти готова: не хватает сохранения пакета как целого и тела. Там же уже есть `start := time.Now()` (строка 67) для длительности.
- Ответ приёма содержит `request_id` и по каждому конверту `{generation, id, status}` — 1С его получает, но **не сохраняет**.
- Идентификатор конверта (`r-…`, 45 символов) одинаков с обеих сторон.

## 3. Пробелы

| № | Пробел | Следствие |
|---|---|---|
| П-1 | 1С не отправляет `X-Request-Id` (веб его принимает) и не хранит `request_id` из ответа | связать «пакет в 1С» с «пакетом на вебе» можно только по времени и составу |
| П-2 | На 1С нет сущности «пакет»: `ПометитьОтправляемыми` помечает конверты, но группа нигде не фиксируется | нельзя ответить «какой пакет ушёл, сколько в нём было, что ответили» |
| П-3 | На 1С хранится только последняя попытка (`Попыток`, `ТекстОтвета`) | история «попытка 1 → 500, попытка 2 → 200» теряется |
| П-4 | На вебе не хранится тело запроса (только `body_sha256` и `bytes`) | «что в пакете» видно лишь на стороне 1С, после успешной отправки тело уходит из поля зрения |
| П-5 | На вебе нет списка пакетов ни в UI, ни в API: `ingest_log` доступен только SQL-запросом | Н-1…Н-3 не выполняются |
| П-6 | Нет состояния каналов: `channel` в `ingest_log` пуст для HTTP-приёма, нет таблицы каналов и активной пробы | Н-6 не выполняется |
| П-7 | Нет страницы «Обмен» в панели 1С | смотреть очередь и пакеты можно только маркерами и COM-запросами |

## 5. Сторона Web: что добавить

### 5.1. Миграция 003

```sql
-- Пакет = один HTTP-запрос приёма
CREATE TABLE IF NOT EXISTS ingest_batches (
  request_id   TEXT PRIMARY KEY,
  received_at  INTEGER NOT NULL,
  remote_addr  TEXT NOT NULL DEFAULT '',
  channel      TEXT NOT NULL DEFAULT 'http',
  level        TEXT NOT NULL DEFAULT '',
  http_code    INTEGER NOT NULL,
  bytes_in     INTEGER NOT NULL DEFAULT 0,
  items        INTEGER NOT NULL DEFAULT 0,
  accepted     INTEGER NOT NULL DEFAULT 0,
  duplicates   INTEGER NOT NULL DEFAULT 0,
  rejected     INTEGER NOT NULL DEFAULT 0,
  duration_ms  INTEGER NOT NULL DEFAULT 0,
  token_prefix TEXT NOT NULL DEFAULT '',
  user_agent   TEXT NOT NULL DEFAULT '',
  response     TEXT NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_batches_received ON ingest_batches (received_at DESC);

-- Тело запроса: нужно, чтобы видеть пакет после того, как 1С его забыла
CREATE TABLE IF NOT EXISTS ingest_payloads (
  request_id  TEXT PRIMARY KEY REFERENCES ingest_batches(request_id) ON DELETE CASCADE,
  body        TEXT NOT NULL,
  truncated   INTEGER NOT NULL DEFAULT 0,
  sha256      TEXT NOT NULL DEFAULT '',
  stored_at   INTEGER NOT NULL
);

-- Состояние каналов на стороне приёма
CREATE TABLE IF NOT EXISTS channel_state (
  name        TEXT PRIMARY KEY,
  enabled     INTEGER NOT NULL DEFAULT 1,
  last_ok_at  INTEGER,
  last_err_at INTEGER,
  last_code   INTEGER,
  last_error  TEXT NOT NULL DEFAULT '',
  checked_at  INTEGER
);
```

Расширение журнала конвертов:

```sql
ALTER TABLE ingest_log ADD COLUMN batch_request_id TEXT NOT NULL DEFAULT '';
ALTER TABLE ingest_log ADD COLUMN level TEXT NOT NULL DEFAULT '';
ALTER TABLE ingest_log ADD COLUMN duration_ms INTEGER NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS idx_ingest_batch ON ingest_log (batch_request_id);
```

`ingest_log.request_id` остаётся, но теперь дублируется в `batch_request_id` явно: смысл разный (пакет против конверта), и это видно читающему SQL.

### 5.2. Что и когда писать

| Момент | Запись |
|---|---|
| Начало `handleIngest` | `request_id` = `X-Request-Id` от 1С, иначе генерируется; фиксируется `started = now` |
| Тело получено | `ingest_payloads` (до 256 КБ, `truncated = 1` если длиннее — лимит `limits.body_bytes` уже 262 144) |
| Каждый конверт | строка `ingest_log` + `batch_request_id` |
| Конец `handleIngest` | `ingest_batches`: коды, счётчики из ответа, `duration_ms` = `now - started`, `response` = тело ответа |

### 5.3. API

| Метод | Путь | Что отдаёт |

| `GET` | `/api/v1/ingest/{request_id}` | пакет + тело запроса + конверты (`id`, `kind`, `status`, `issue`, `generation_id`) + что записано в БД + ответ |

### 5.5. Retention

`ingest_batches` и `ingest_payloads` чистятся вместе с `ingest_log` (`logDays`, по умолчанию 90). Тела — первыми: они занимают больше всего. Правило то же, что в `Retention`: сначала свёртка, потом удаление.

## 6. Сквозная корреляция

```
1С: Пакет = pkt-7f3a1b2c-1794127600
     ├─ X-Request-Id: pkt-7f3a1b2c-1794127600       (генерирует 1С)
     ├─ конверты: r-AAAA…, r-BBBB…                   (id уже стабильны)
     └─ регистр ПерфОбменПакет: код 200, мс 640, канал HTTPS, уровень A, RequestId …

Web: ingest_batches.request_id = pkt-7f3a1b2c-1794127600
     ├─ ingest_payloads.body = исходный JSON
     ├─ ingest_log.batch_request_id = тот же
     └─ ответ: {"accepted":11,"request_id":"…","items":[{"id":"r-AAAA…",…}]}

Проверка: один и тот же request_id и те же id конвертов — сверка одним взглядом.
```

Требование к 1С: **не переиспользовать** `request_id` между попытками. Повтор того же пакета — новый `pkt-…`, иначе на вебе два разных запроса сольются в один.

## 7. Быстрый цикл проверки

| Сценарий | Что делать | Что смотреть в 1С | Что смотреть на вебе |
|---|---|---|---|
| Успех | `/C "ПерфОбменОтправить"` | маркер `exchange-packet:…:200`, вкладка «Пакеты» | `/ingest` → строка → вкладки «Запрос», «В базе» |
| Нет токена | очистить секрет, отправить | `exchange-run:… ;ключ не настроен`, очередь цела | новых пакетов нет |
| Неверный токен | токен с опечаткой | код 401 в пакете и в очереди | `/ingest` → код 401, статус `rejected`, `error: token_unknown` |
| Битый конверт | испортить `measured_at_utc` в очереди | код 400 в пакете, текст ошибки разбора | `/ingest/{id}` → «Ответ» с текстом Go-ошибки |
| Частичный приём | 11 конвертов, один с плохим `scenario` | код 207, `Принято` = 10, `Отклонено` = 1 | «Конверты»: 10 ok, 1 rejected с причиной |
| Нет сети | выключить адрес в константе | `Попыток` растёт, `СледующаяПопытка` сдвигается, канал `Доступен = Ложь` | пакетов нет; `/channels` показывает ошибку |
| Отказ проверки TLS | адрес с чужим сертификатом | `Уровень = B`, маркер `exchange-tls-downgrade` | пакет проходит, `level` в `ingest_batches` = `B` |

Все семь сценариев проверяются без SQL и без чтения маркеров вручную — это и есть критерий «быстро».

|---|---|---|---|
| **Н1. Корреляция** | `X-Request-Id` в 1С, `ingest_batches` + `ingest_payloads` на вебе, `GET /api/v1/ingest`, `/ingest` (список) | 1С ≈ 40 строк, веб ≈ 300 (приём заголовка и замер времени уже есть) | без идентификатора остальное не сходится; даёт Н-1, Н-2, Н-4 |
| **Н2. Пакет в 1С** | регистр `ПерфОбменПакет`, правки `ОтправитьОчередь`/`Разметить`/`РазобратьОтвет`, режим `/C "ПерфОбменПакеты"` | ≈ 220 строк | даёт Н-5 и вторую половину Н-2 (что сформировали) |
| **Н3. Карточка пакета** | `/ingest/{request_id}` + блок «В базе», страница `/ingest/{id}` в UI, ссылка из витрины стенда | ≈ 250 строк | замыкает Н-3 и Н-4: видно, что именно записалось |
| **Н4. Каналы** | регистр `ПерфОбменКанал`, таблица `channel_state`, `/api/v1/channels`, проба, вкладка в панели | ≈ 260 строк | Н-6; полезно и без остального, но зависит от Н2 (канал пишется в пакет) |

Итого ≈ 1130 строк, из них Go/HTML ≈ 860, BSL ≈ 270. Этапы независимы после Н1.

## 9. Риски и ограничения

| Риск | Что делаем |
|---|---|
| Тела пакетов занимают место | лимит 256 КБ на пакет (как `limits.body_bytes`), `truncated` помечает усечение, хранение 90 дней вместе с `ingest_log` |
| Тело содержит замеры стенда, но не секреты | проверка: в теле нет `Authorization` (он в заголовке и не сохраняется); тест «в `ingest_payloads` нет `Bearer`» |
| `request_id` от клиента можно подделать | он не влияет на права; при коллизии — `ON CONFLICT` дописывает суффикс и пишет `issue` |
| Журнал пакетов на 1С растёт | хранить 30 дней, чистить в `ЗавершитьПрогон` или отдельным режимом |
| Чтение `В базе` требует запросов к нескольким таблицам | один запрос на карточку: `results`/`history`/`stand_passports` по `generation_id` из `ingest_log` |

## 10. Критерии готовности

1. Отправка 11 конвертов даёт **один** пакет в 1С и **одну** строку `ingest_batches` с тем же `request_id`.
2. По `request_id` открывается карточка: тело запроса, 11 конвертов со статусами, 11 записей в `results` и 11 в `history`, ответ сервера.
3. Неудачная отправка (401/400/сеть) видна на обеих сторонах с причиной, без SQL.
4. Состояние всех восьми каналов видно в одном месте, с временем последней проверки и кодом.
5. Ни один сценарий из § 7 не требует чтения маркеров вручную.
