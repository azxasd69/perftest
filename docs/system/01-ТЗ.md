Документ задаёт требования **к конфигурации в целом**. Детальные формулировки требований панели
(ФТ-01…ФТ-15, НФТ, отчёты, паспорт, каркас) остаются в `../spec/ТЗ.md`; требования к обмену с
порталом — в `../spec/ТЗ_доработка_интеграция.md`. Здесь — то, чего в этих документах нет:
границы системы, цели с измеримыми признаками достижения, требования уровня подсистем, стадии,
порядок приёмки и комплект документации.

## 1. Общие сведения

| Поле | Значение |
|---|---|
| Наименование | конфигурация `PerfTest` — сравнительные замеры производительности 1С:Предприятия 8.3 |
| Обозначение | `PerfTest` (репозиторий `azxasd69/perftest`), расширение оформления `PerfStyle` |
| Заказчик | владелец стенда (частное лицо), замеры выполняются на собственной машине |
| Исполнитель | разработчик конфигурации (в текущем контуре — агент под руководством владельца) |
| Основание | потребность сравнивать сборки и настройки платформы между собой на воспроизводимых замерах |
| Смежные системы | портал `perfd` (`azxasd69/perfd`) — приём и витрина замеров; `1C:EDT` — проверка модели |
| Состояние | действующая система, версия 1.42 от 09.11.2026 |
| Лицензия | MIT (код и документация) |

Документ не является договором: стороны — владелец стенда и исполнитель, работающего контура
заказчика (юридического лица) нет, поэтому реквизиты договора и сроки в календарных датах не
фиксируются, а фиксируются стадии и признаки их завершения (§8).

## 2. Назначение и цели

### 2.1. Проблема

Сравнение «быстрее или медленнее» на глаз не работает: разница между сборками платформы и
настройками сервера лежит в единицах и десятках процентов, а шум планировщика, кэшей и файловой
системы того же порядка. Без одинакового набора операций, одинаковых объёмов и статистики по
нескольким прогонам вывод получается произвольным.

### 2.2. Назначение

Дать владельцу стенда воспроизводимый способ измерить скорость типовых операций 1С на конкретной
машине, сборке платформы и режиме клиента, сравнить результат с базой сравнения и объяснить
разницу через среду замера (паспорт стенда).

### 2.3. Цели и признаки их достижения

| ID | Цель | Признак достижения (проверяемый) |
|---|---|---|
| Ц-1 | Сравнение стендов по одной метрике | медиана и «мс на 1000 единиц работы» считаются для каждого из 11 сценариев; сравнение двух стендов даёт таблицу с колонкой дельты |
| Ц-2 | Замер воспроизводим на другом стенде | прогон на другой машине даёт числа того же порядка; паспорт стенда объясняет отличие (процессор, диск, память, версия платформы) |
| Ц-3 | Результат не зависит от того, кто нажал кнопку | интерактивный прогон, автопрогон `/C ПерфАвтоПрогон` и автономная обработка `ПерфРаннер` дают одинаковую методику расчёта |
| Ц-4 | История не теряется | замеры хранятся в регистрах без перезаписи; повторная отправка на портал не создаёт дубликатов |
| Ц-5 | Результат виден вне машины замера | конверты результатов и паспортов принимаются порталом, витрина показывает замеры и рейтинги |
| Ц-6 | Работоспособность подтверждается машинно | 4 джобы CI (политика выгрузки, XML/версия/ссылки, синтаксис BSL, JS-мост) зелёные на каждом коммите |

### 2.4. Что не является целью

- Аттестация оборудования и «паспорт железа» как официальный документ: паспорт стенда — снимок
  среды замера для объяснения разницы, а не средство приёмки сервера.
- Воспроизведение прикладной нагрузки конкретной конфигурации (УТ, ERP, БП): сценарии синтетические.
- Замена инструментов профилирования платформы (технологический журнал, ЦУП, APDEX): конфигурация
  отвечает на вопрос «стало ли быстрее», а не «почему именно медленно».

## 3. Характеристика объекта и границы

| Параметр | Значение | Следствие для требований |
|---|---|---|
| Вариант ИБ | файловая | нет серверного кластера, нет разделения на сервер/клиент по сети; фон и замер делят один процесс |
| Платформа | 8.3.27.2342 (основная), 8.5.4.1306 (проверочная) | формат выгрузки XML 2.20 — требование `1C:EDT`; 8.5.4 повышает формат базы, нужна отдельная копия |
| Клиенты | толстый `1cv8.exe`, тонкий `1cv8c.exe` | замер выполняется на сервере, интерфейс — HTML-поле; веб-клиент не поддерживается |
| ОС | Windows 10/11 x64 | часть сведений паспорта — только через WMI; на Linux WMI нет, данные берутся из `/proc` |
| Пользователь | один, без разделения ролей | права не настраиваются, конфигурация загружается целиком |
| Разработка | выгрузка в файлы + `1C:EDT` | любое изменение проходит загрузку в базу и проверку модели |

Границы системы:

```text
      ┌────────────────────────── конфигурация PerfTest ──────────────────────────┐
      │  панель и кокпит  →  замеры (сервер)  →  регистры  →  отчёты и паспорт    │
      └───────────────┬───────────────────────────────────────────┬───────────────┘
                      │ HTML-поле (внутри формы)                  │ конверты (очередь)
                      ▼                                           ▼
              пользователь в сеансе 1С                    портал perfd (внешняя система)
```

Вне границ: правка типовых конфигураций, работа с чужими базами, публикация на веб-сервере,
мобильный клиент, интеграции с внешними учётными системами.

## 4. Требования к системе в целом

| ID | Требование | Почему так |
|---|---|---|
| ТС-01 | Измерения выполняются в серверном контексте; клиент не считает метрики | иначе панель, автопрогон и `ПерфРаннер` разойдутся в результатах |
| ТС-02 | Результат замера не зависит от оформления и темы интерфейса | измеряемая операция и отрисовка разделены |
| ТС-03 | Конфигурация работает без внешних зависимостей, кроме платформы и инструментов в `tools/` | стенд должен подниматься на чистой машине |
| ТС-04 | Отсутствие данных не ломает отчёт: пустое поле остаётся пустым, причина пишется в замечания | неполный паспорт лучше падения страницы |
| ТС-05 | Любая фоновая операция имеет таймаут и путь деградации | файловая ИБ: зависший фон блокирует интерфейс |
| ТС-06 | Обмен с порталом не влияет на сохранность замера | при недоступности сети замер пишется без конверта |
| ТС-07 | Секреты и адреса не попадают в код, выгрузку и документацию | репозиторий публичный |
| ТС-08 | Каждая версия оставляет след: тег, запись `CHANGELOG.md`, шапки документов | по расхождению версий уже терялось состояние (1.22 против 1.42) |

| Интерактивный прогон | запуск одной карточки, всех подряд, отмена; прогресс по прогонам и чанкам | `ФТ-03`–`ФТ-08`, `ФТ-13`, `ФТ-14` | `НачальнаяСтраница`, `ПерфСценарии` |

| Обмен с порталом | очередь конвертов `result`/`passport`/`history`, 9 каналов, повторы, идемпотентность, подпись | `../spec/ТЗ_доработка_интеграция.md` §3–§9 | `ПерфОбмен`, `ПерфОбменТранспорт`, `ПерфОбменШифр` |
| Автономный прогон | та же методика без интерфейса — обработка `ПерфРаннер` со своим CSV | `ФТ-12` | `DataProcessors.ПерфРаннер`, форма `ФормаРаннера` |
| Обслуживание | очистка данных, разбор ошибок журнала регистрации, журнал ошибок конфигурации | — (эксплуатационное) | `ПерфОбслуживание`, `ПерфЖурнал` |

Требование к полноте каталога: перечень сценариев, их порции и единицы — часть контракта метрики.
Изменение порции допустимо, но обязано оставить пометку в истории («порция изменилась»), иначе
сравнение с прежними замерами станет ложным.

## 6. Требования к данным

| ID | Требование |
|---|---|
| ТД-01 | Ключ результата — `Стенд × ВерсияПлатформы × Сценарий`; повторный замер заменяет запись |
| ТД-02 | Ключ истории — `Стенд × Сценарий × ДатаЗамера`; записи только добавляются |
| ТД-03 | Метрика сравнения — `НаЕдиницуМс` = медиана / (порция / 1000); округление до 3 знаков |
| ТД-04 | Паспорт стенда хранится поколениями: смена среды не затирает прежнее описание |
| ТД-05 | Конверт обмена неизменяем после постановки в очередь; повтор отправки не создаёт дубликат на приёмнике |
| ТД-06 | Ошибки конфигурации сохраняются в регистре `ПерфОшибки`; при недоступности регистра — в файл |
| ТД-07 | Тот же `id` с тем же телом — `duplicate` (200), тот же `id` с другим телом — `conflict` (409); схема не 1 — `415` |
| ТД-08 | Тело конверта: `result` до 4 КБ, `passport` до 20 КБ, `history` до 256 КБ; батч — до 50 конвертов и 256 КБ |
| ТД-09 | Стенд идентифицируется двумя отпечатками: читаемым (для людей и карточки) и каноническим (латинские ключи, для слияния стендов на портале); в каноническом нет версии конфигурации, объёма базы, порции и числа повторов |
| ТД-10 | Подпись `sig` необязательна: пустой ключ HMAC — не ошибка, конверт уходит с `sig = "none"` |
| ТД-11 | Очередь обмена хранит тело, хеш и размер конверта; хеш пересчитывается перед отправкой, расхождение даёт статус `Ошибка` |

## 7. Требования к интерфейсам

| ID | Интерфейс | Требование |
|---|---|---|
| ТИ-01 | Пользовательский | панель открывается одним окном; навигация — боковое меню и палитра; тема запоминается между сеансами |
| ТИ-02 | HTML-поле | страница приходит готовым документом; взаимодействие — через мост (`data-pf`), а не инлайновые обработчики |
| ТИ-03 | Обмен (HTTP) | `POST /api/v1/ingest` пакетом, ответ 200 с числом принятых, 401 при неверном токене, 400 при нарушении контракта, 409 при конфликте тела, 413 при превышении размера, 415 при неизвестной схеме |
| ТИ-04 | Файловый приём | конверт кладётся в `in/`, подтверждение — `<id>.ack` в `out/` |
| ТИ-05 | Служебные режимы | `/C` режимы (`ПерфАвтоПрогон`, `ПерфОчисткаДанных`, `ПерфОшибкиЖурнала`, `ПерфОбмен…`) не мешают обычной работе |
| ТИ-06 | Инструменты | все операции с базой и выгрузкой выполняются скриптами `tools/`, а не ручными действиями в конфигураторе |
| ТИ-07 | Движок HTML-поля | страницы собираются только из поддерживаемых свойств: нет `flex-gap`, `oklch`, `color-mix`, `clamp`, `backdrop-filter`; `sticky` не работает — закрепление через `fixed` и распорку; `Height` поля игнорируется — `VerticalStretch`; только системные шрифты |
| ТИ-08 | Тема и панель | тема (`pf-light`/`pf-dark`) ставится сервером в разметку по константе, а не скриптом; состояние свёрнутости панели хранится в константе и переживает перезапуск сеанса |

## 8. Нефункциональные требования

| ID | Категория | Требование | Как проверяется |
|---|---|---|---|
| НФ-01 | Производительность | полный прогон 11 сценариев при 2 повторах — не более 60 с на референсной машине (факт 1.42: 11–18 с); страница отчёта — не более 0,3 с (факт ≈ 0,11 с); смоук шести форм — не более 10 с (факт 5,9 с) | замер автопрогона, смоук |
| НФ-02 | Отзывчивость | панель открывается до 3 с; прогресс обновляется не реже раза в секунду; опрос моста 0,25 с во время прогона и 2 с в покое | живой прогон мышью |
| НФ-03 | Шум измерения | медиана сценария не опускается ниже 20 мс, иначе разница сборок тонет в шуме таймера | профиль порций |
| НФ-04 | Надёжность | сбой одной карточки не останавливает очередь; отмена освобождает блокировку | сценарий «Стоп» |
| НФ-05 | Переносимость | Windows и Linux; файловая и клиент-серверная ИБ; толстый и тонкий клиент | профиль среды, `ПерфСреда` |
| НФ-06 | Безопасность | секреты вне кода; TLS с доверием к сертификату портала; подпись конверта HMAC-SHA-256 (проверка подписи на приёмнике — требование, реализовано не полностью, см. §12) | самотест, живая отправка |
| НФ-07 | Сопровождаемость | модуль отвечает за одну зону; правка поведения сопровождается записью в `CHANGELOG.md` | ревью, CI |
| НФ-08 | Документируемость | у каждого документа есть тип, статус, версия сверки и место в индексе | `check-doc-headers.py` (этап 6) |
| НФ-09 | Паспорт не блокирует замер | сбор полного паспорта — не более 5 с (факт 1,1–1,15 с); барьер перед замером — 0,5 с в панели и 30 с в автопрогоне, при таймауте пишется только быстрая фаза | маркеры сбора, живой прогон |

Дополнительно к машинным гейтам: живой UI-прогон мышью (`tools/ui-scenario.ps1`) — единственная
проверка, которая ловит недоступные кнопки, пустые таблицы и обращения к неинициализированным
переменным. Приёмка версии без живого прогона неполна.

## 11. Требования к документированию

Комплект: техническое задание (этот документ), архитектура, техническое решение, паспорт системы,
детальные требования (`../spec/`), устройство (`../design/`), проверки (`../verify/`), ADR
(`../decisions/`), эксплуатация (`../ops/`), индекс `../README.md`, `CHANGELOG.md`.

Правила: один документ — одна зона ответственности; утверждения о поведении сопровождаются версией
сверки; «что требуется» и «как сделано» не смешиваются; секреты и реальные адреса не публикуются.

## 12. Ограничения и допущения

- Клиент-серверный вариант и Linux описаны и частично проверены; полная матрица стендов не подтверждена.
- Сценарии синтетические: прикладная нагрузка конкретной конфигурации ими не воспроизводится.
- В файловой ИБ фон и замер делят процесс: одновременная автодосылка во время прогона запрещена.
- Платный комплект 1С MCP и внешние информационные базы недоступны: часть проверок выполняется вручную.
- Портал рассчитан на один сервер: резервное копирование — решение владельца, автоматического бэкапа нет.

Расхождения требований с реализацией (проверено по коду 1.42 и портала):

| Требование | Состояние | Следствие |
|---|---|---|
| Проверка подписи HMAC на приёмнике | приёмник её **не выполняет** (только SHA-256 токена в постоянном времени) | целостность обеспечивает TLS и токен; подпись защищает только от подмены на стороне отправителя |
| Предел 12 попыток отправки | в коде счётчик **не ограничен** | при постоянной ошибке конверт повторяется каждые 900 с бесконечно |
| CMS-шифрование для HTTP80 | фактически включается только для SMTP | канал HTTP80 не годится для передачи чувствительного тела |
| Каналы 2–8 живьём | проверены на уровне «канал отвечает» | полноценных стендов под FTP/FTPS, SMTP, SFTP, WebDAV не было |
| Обратный канал команд с портала | не реализован | обновление паспорта и запрос истории инициируются только из 1С |
| Чтение подтверждений по IMAP | не реализовано | разбираются только локальные `out/<id>.ack` |
| Отправка DNS и спула | выполняется внешней утилитой, её в репозитории нет | канал DNS в поставке не работает без утилиты |
