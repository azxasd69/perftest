Документ сквозной: описывает и сторону 1С, и портал, потому что половина решений (контракт конверта,
идемпотентность, поколения стенда, доверие TLS) существует только на стыке. Решения приведены с
альтернативами — это отличает техническое решение от описания кода.

## 1. Область и принципы

| Принцип | Следствие |
|---|---|
| Один замер — один источник истины | метрика считается на сервере 1С, портал только хранит и агрегирует |
| Доставка не отменяет замер | сначала транзакция результата, потом конверт; при сбое обмена замер сохраняется |
| Повторная доставка безопасна | идентификатор конверта уникален, приём идемпотентен |
| Контур обслуживает один человек | минимум процессов, нет очередей сообщений и брокеров |
| Секреты не в коде | токен, HMAC и пароли каналов — в регистре секретов на стороне 1С, в окружении — на стороне портала |

## 2. Состав решения

| Компонент | Технология | Назначение | Репозиторий |
|---|---|---|---|
| Конфигурация `PerfTest` | 1С:Предприятие 8.3, выгрузка в файлы | замеры, интерфейс, паспорт, очередь обмена | `azxasd69/perftest`, `src/` |
| Расширение `PerfStyle` | расширение конфигурации (стиль) | токены цветов кокпита | `azxasd69/perftest`, `ext/PerfStyle` |
| Портал `perfd` | Go 1.27.3 + SQLite (modernc, без cgo) | приём, хранение, витрина, API | `azxasd69/perfd` |
| Инструменты | PowerShell 7, Python 3.14, Node | загрузка, проверки, прогоны, UI-сценарии | `perftest/tools` |
| CI | GitHub Actions, 4 джобы | гейты качества на каждом коммите | `.github/workflows/ci.yml` |

Портал сознательно не использует Docker и внешнюю СУБД: контур — один VPS с 1 vCPU и 865 МБ памяти,
SQLite в WAL-режиме даёт нужную нагрузку при нуле администрирования.

## 3. Ключевые решения и альтернативы

Формат — сокращённый ADR: контекст, решение, что отклонено, последствия. Полные ADR — в
`../decisions/`.

| № | Вопрос | Решение | Отклонённые альтернативы | Последствия |
|---|---|---|---|---|
| Р-1 | Где считать метрику | на сервере 1С, в `ПерфСценарии` | считать на клиенте; считать на портале | один код замера на все пути; портал не зависит от платформы |
| Р-2 | Как строить интерфейс | HTML-документ в поле HTML, нативные кнопки — гибрид | только нативные формы 1С | свобода вёрстки и темы; мост и его грабли — цена |
| Р-3 | Как передавать события страницы в 1С | мост `PF1C` + `data-pf` атрибуты | инлайновые `onclick` в разметке | одна точка обработки, переживает перерисовку |
| Р-4 | Как собирать паспорт среды | конвейер «среда → план → блоки», две фазы, фон | собирать синхронно при старте | панель открывается сразу; неполный паспорт помечается |
| Р-5 | Как доставлять результаты | push-конверты через очередь в базе 1С, лестница из 9 каналов | забирать порталом (pull); один жёсткий HTTP-канал | работает за NAT и без входящих портов; нужна идемпотентность |
| Р-6 | Как обеспечить идемпотентность | уникальный `id` конверта формата `r-…`/`p-…`/`h-…`, проверка до записи | сравнение по содержимому; дедупликация по времени | повтор безопасен, дубликатов нет |
| Р-7 | Как хранить на портале | SQLite + схема с `*_v2` таблицами и `schema_meta` | PostgreSQL; файлы + индексы | ноль администрирования; предел — один сервер |
| Р-8 | Как различать среды замера | поколения стенда (`stand_generations`) | одна запись стенда с перезаписью паспорта | прежние замеры не смешиваются с новыми условиями |
| Р-9 | Чем доверять TLS | сертификат CA портала хранится в регистре 1С | сертификат в хранилище ОС; отключить проверку | перенос базы переносит доверие; деградация до уровня B фиксируется маркером |
| Р-10 | Чем подписывать конверт | HMAC-SHA-256 на ключе из регистра | RSA-подпись; отсутствие подписи | достаточно для контроля целостности; ключ общий |
| Р-11 | Как принимать файлы и почту | те же конверты через `in/`+`out/`, Maildir, DNS TXT по TCP | только HTTP | контур работает при закрытом 443; больше кода на портале |
| Р-12 | Как обслуживать данные | ретенция: свёртка детального ряда, удаление по сроку | хранить всё; удалять всё старше месяца | витрина остаётся быстрой, история не теряется целиком |

## 4. Сторона 1С: как сделано

### 4.1. Замер

- Каталог `СписокСценариев` — массив структур (не `ТаблицаЗначений`: таблицу нельзя передать с
  сервера на клиент в тонком клиенте). 11 сценариев, порции от 5 документов до 25 000 итераций.
- `ВыполнитьПрогон` выполняет порцию чанками, каждый чанк — отдельный серверный вызов: это даёт
  прогресс и возможность отмены. Медиана считается по временам прогонов, а не по чанкам.
- Замеры идут фоновым заданием; `ОпросПрогрессаФон` разбирает строки «РЕЗУЛЬТАТ:/Чанк», поэтому в
  тонком клиенте работает та же схема, что в толстом.

### 4.2. Запись результата

```text
НачатьТранзакцию
  набор ПерфРезультаты.Записать(Истина)
  ПерфОбмен.ПоставитьВОчередьРезультат(...)
ЗафиксироватьТранзакцию
при исключении: ОтменитьТранзакцию, набор записывается повторно БЕЗ конверта
после транзакции: паспорт стенда, история замера
```

Паспорт и история вынесены за транзакцию намеренно: паспорт собирает WMI и COM, внешние вызовы
внутри транзакции держали бы блокировки файловой ИБ.

### 4.3. Паспорт стенда

Схема 3, 71 реквизит, источники: `СистемнаяИнформация`, WMI (`Win32_OperatingSystem`,
`Win32_Processor`, `Win32_ComputerSystem`, диски), `/proc` и `/sys` на Linux, сведения об ИБ.
Отсутствующие данные остаются пустыми, причина — в замечаниях сбора. Пароль в строке соединения
маскируется. Смена среды создаёт новое поколение, прежнее описание сохраняется.

### 4.4. Интерфейс

`ПерфUI.Документ` собирает полный HTML-документ: `<html>`, `<head>` со стилями и скриптами, `<body>`
с телом страницы. Поле HTML показывает только полный документ: фрагмент оно трактует как адрес и
показывает пустую страницу — эта ошибка уже случалась и отражена в `../design/Реализация.md` §8.

Темы: базовые токены и блок `html.pf-dark` в одном `ПерфUI.Стили()`; переключение — класс на
`<html>`, выбор сохраняется и сообщается в 1С командой `theme:<имя>`.

### 4.5. Обмен

- Очередь — регистр `ПерфОчередьОбмена`: вид конверта, тело, статус, попытки, пометка отправки.
- Лестница каналов строится из `ПерфОбменКанал` (приоритет) и сужается профилем среды.
- Транспортные ошибки возвращают конверт в «Ожидает» с паузой; ошибки контракта (400) и доступа
  (401) — в «Ошибка» с текстом; исчерпание попыток — отдельный статус.
- Отправка запускается из четырёх точек: регламентное задание (интервал 900 с), старт сеанса,
  после автопрогона, кнопка в журнале обмена. Автодосылка не запускается во время прогона.

### 4.6. Определение среды

`ПерфСреда.Определить` возвращает отпечаток `ОС-вариант-режим` (`win-file`, `lin-srv-thin`),
возможности (WMI, `/proc`, `pscp`, `openssl`, почта) и текст для журнала. `Профиль` формирует только
запреты, `Применить` идемпотентно выключает нерабочие каналы и пишет в журнал запись «Событие».

## 5. Сторона портала: как сделано

### 5.1. Процесс и режимы

Один бинарь `perfd`, режимы запуска:

| Режим | Назначение |
|---|---|
| по умолчанию | HTTP-сервис: приём, API, витрина, метрики |
| `-watch` | файловый приём: обход `in/`, подтверждения `<id>.ack` в `out/`, архив обработанных |
| `-mail` | почтовый приём: Maildir `perfing` → конвейер, подтверждение в `perfack` |
| `-dns` | DNS-приём TXT-конвертов по TCP |
| `-retention` | свёртка детального ряда в месячные агрегаты, удаление по сроку |
| `-export` | снимок базы в `.gz` с манифестом |
| `-check` | открыть базу и напечатать счётчики |
| `-alerts` | оповещения: почта, webhook, метрики `:9091` |

Конфигурация — переменные окружения `PERF_*`: адрес (`127.0.0.1:8080`), база, префикс публикации
(`/perf`), лимит тела (256 КБ), схема конверта, версия формулы ИИ, хеш токена приёма, ключ HMAC,
список разрешённых каналов, сроки хранения (12 месяцев для замеров), каталог почты, зона DNS.

### 5.2. Хранилище

| Таблица | Содержимое |
|---|---|
| `schema_meta` | версия схемы и применённые миграции |
| `stands`, `stand_generations` | стенд и его поколения среды |
| `stand_passports` | паспорт поколения (JSON-свойства) |
| `results`, `history`, `aggregates` (+ `*_v2`) | текущие замеры, ряд истории, месячные агрегаты |
| `ingest_log` | журнал приёма: кто, когда, сколько принято, дубликаты |
| `tokens`, `api_keys` | хеши токенов и ключи API |
| `cmd_queue` | команды стенду (на будущее использование) |
| `audit_log`, `scenarios` | аудит действий и справочник сценариев |

Индексы построены под витрину: `history (measured_at DESC, per_unit_ms DESC)` для топа,
`history (stand_id, scenario, measured_at DESC)` для истории сценария, `passport (generation_id,
is_current)` для текущего описания стенда.

### 5.3. HTTP-поверхность

| Группа | Маршруты |
|---|---|
| Служебные | `/healthz`, `/readyz`, `/healthz/channels`, `/metrics` |
| Приём | `POST /api/v1/ingest` (пакет), `POST /api/v1/import`, `POST /ingest-plain` |
| Чтение | `/api/v1/meta`, `/api/v1/status`, `/stands`, `/stands/{slug}`, `/stands/{slug}/results`, `/stands/{slug}/history`, `/top`, `/ratings`, `/compare` |
| Администрирование | `POST /api/admin/purge` |
| Витрина | `/`, `/stands`, `/stands/{slug}`, `/stands/{slug}/history/{scenario}`, `/top`, `/about` |

Публикация — под префиксом `/perf`; 1С ходит на `/api/v1/…` без префикса, поэтому оба варианта
поддерживаются одной настройкой `PERF_BASE_PATH`.

### 5.4. Приём конверта

1. Проверка размера и разбора JSON (лимит тела, строгие типы: `measured_at_utc` — целое).
2. Проверка идентификатора (`^[rph]-[A-Za-z0-9_-]{43}$`) и отпечатка стенда (64 hex).
3. Проверка подписи, если ключ HMAC задан.
4. Проверка существования `id` в `ingest_log` — до записи, иначе повтор сбрасывал бы счётчики.
5. Запись паспорта поколения, результатов, истории — в одной транзакции.
6. Ответ: `200` с `accepted` и `duplicates`, `401` при неверном токене, `400` с текстом нарушения.

## 6. Стык: конверты и каналы

### 6.1. Виды конвертов

| Вид | Когда | Содержимое |
|---|---|---|
| `result` | после каждого замера | сценарий, медиана, «мс/тыс.», порция, единица, повторов, минимум, максимум, `measured_at_utc`, `runs_string`, признак подписи |
| `passport` | при смене поколения среды | `{schema, properties}` с именами реквизитов 1С (71 реквизит) |
| `history` | при досылке истории | массив замеров с датами |

### 6.2. Каналы

| Канал | Транспорт | Особенность |
|---|---|---|
| HTTPS, HTTPS8443, PROXY, HTTP80 | `HTTPСоединение` | HTTP80 требует CMS-конверта (`openssl`) |
| WEBDAV | HTTP `PUT` во временный файл + `MOVE` | подтверждение через `out/` |
| FTP/FTPS | `FTPСоединение` | открытый FTP запрещён профилем |
| SMTP | `ИнтернетПочта` | вложение через `Сообщение.Вложения.Добавить`, не конструктором |
| SFTP | внешний процесс `pscp -batch` | нужен `pscp` в `PATH`, иначе канал выключается |
| DNS | внешняя утилита `perf-push` | `perfd -dns` слушает только TCP |

### 6.3. Идемпотентность и повторы

Идентификатор конверта генерируется один раз при постановке в очередь и не меняется. Приёмник
проверяет `id` до записи, поэтому повтор после сетевого сбоя возвращает `duplicates: 0` или `1`, но не
создаёт второй замер. На стороне 1С повтор идёт с паузой; зависшие записи снимаются по пометке
отправки, а не по времени создания.

## 7. Безопасность

| Аспект | Решение |
|---|---|
| Аутентификация приёма | токен; на портале хранится только SHA-256, сравнение постоянного времени |
| Целостность | HMAC-SHA-256 по телу конверта; ключ в регистре `ПерфОбменСекрет` |
| Транспорт | HTTPS; доверие к CA портала из регистра `ПерфОбменСертификат`, деградация до уровня B фиксируется маркером `exchange-tls-downgrade` |
| Секреты каналов | регистр секретов; в файловой ИБ — файл с ограниченным доступом, каталог из константы |
| Публикация | лимит тела 256 КБ, валидация схемы, журнал приёма и аудит |
| Документация | адреса, домены и токены заменены плейсхолдерами (`perf.example.com`, `198.51.100.10`) |

## 8. Развёртывание и эксплуатация

| Задача | Как |
|---|---|
| Создать базу | `ib.ps1 -Action create -Base <каталог> -PlatformVersion 8.3.27.2342` |
| Загрузить конфигурацию | `ib.ps1 -Action load -Dir src` |
| Поставить расширение | `ext-load.ps1` |
| Проверить здоровье | `/healthz`, `/readyz`, `/healthz/channels`, `/metrics` |
| Смотреть состояние обмена | страница «Журнал обмена» в кокпите: каналы, очередь, ошибки, проба |
| Очистить данные тестов | `/C "ПерфОчисткаДанных"` |
| Разобрать ошибки журнала регистрации | `/C "ПерфОшибкиЖурнала:24"` |
| Обновить портал | атомарный релиз каталогом + переключение символической ссылки, откат — предыдущий каталог |

Резервное копирование портала автоматически **не выполняется** — осознанное решение владельца
(риск потери базы принят). Логи хранятся 7 дней, замеры — 12 месяцев.

## 9. Проверки и остаточный риск

| Проверено | Чем |
|---|---|
| Синтаксис BSL, загрузка, проверка модулей | BSL LS 1.0.7, `ib.ps1`, CI |
| Модель конфигурации и расширения | `1cedtcli validate`, 0 «Ошибок конфигурации» |
| Интерфейс и живой прогон | `tools/ui-scenario.ps1`, 11/11 замеров, «Стоп», история, каналы |
| Обмен | живая отправка, `accepted` = `sent`, `duplicates 0`, повтор даёт `sent=0` |
| Переносимость | Linux CLI, клиент-серверная ИБ, тонкий клиент |
| Приём файлов и почты | файловый канал с подложенным `.ack`, почтовый и DNS-каналы на стенде |

Не проверено (остаточный риск): каналы 2–8 вживую (нет FTP/SMTP/SFTP/WebDAV-стенда и сертификата
CMS), полная матрица «Windows/Linux × файловая/серверная», поведение при больших объёмах истории на
портале, восстановление базы после сбоя без бэкапа.

## 10. Ограничения

- Максимум один сервер портала: SQLite и один процесс, горизонтального масштабирования нет.
- Замеры синтетические: прикладная нагрузка не воспроизводится.
- Формальные замечания EDT (запросы в цикле) приняты осознанно для сценариев замера.
- В файловой ИБ фон и замер делят процесс, поэтому автодосылка отключается на время прогона.
