## 1. Цель и что считается порядком

Цель — чтобы на любой вопрос «как это работает / почему так / чем проверено» был **один**
документ, который **найдён за один переход** и **не врёт про версию**.

Порядок фиксируем шестью измеримыми признаками:

1. Один канон — документация живёт в репозитории, а не в трёх копиях.
2. У каждого документа есть шапка: тип, статус, версия, на которой проверен, дата ревизии.
3. Ни одного документа без входящей ссылки из индекса (`docs\README.md`).
4. Версия в шапке не расходится с `src\Configuration.xml` (проверяется машиной).
5. Ни одного «датированного раздела в конце» вместо обновления тела документа.
6. Ноль файлов, которые не документ и не артефакт по правилам (дампы страниц, старые превью, копии чужих README).

Текущее состояние по этим признакам: 1 — нарушен (4 пригодных места, 8 из 10 документов
разошлись), 2 — 15 из 25 имеют шапку, статус есть у 8, 3 — 10 документов без ссылок, 4 — нарушен
(1.22/1.28/1.29/1.37 против 1.42), 5 — нарушен (14 датированных разделов в `Проверки.md`,
3 в `Реализация.md`), 6 — нарушен (136 дампов страниц, 5 версий превью логотипа, 2 чужие копии).

## 2. Принципы (принимаются один раз и действуют дальше)

| № | Принцип | Что это запрещает |
|---|---|---|
| П1 | **Один канон.** Документ существует в одном месте; остальное — ссылки | копировать документ в проект и в репозиторий |
| П2 | **Один дом — один вопрос.** У документа одна зона ответственности | писать «как сделано» в ТЗ и «что требуется» в Проверках |
| П3 | **Документ = утверждение о поведении.** Значит, у него есть «проверено на» | описывать намерения как факты |
| П4 | **Обновляем тело, а не дописываем хвост.** История — в `CHANGELOG.md` | разделы «## Тема (09.11.2026, версия 1.42)» в конце |
| П5 | **Ссылки только относительные** внутри репозитория | пути `1c\perf-test\src` в опубликованных документах |
| П6 | **Нет документа без входа.** Новый файл — сразу в индекс | «положу рядом, потом разберутся» |
| П7 | **Мусор не хранится.** Дампы, превью, копии — 30 дней максимум | складывать в `scratch` «на всякий случай» |
| П8 | **Секреты не документируются.** Адреса, токены, пароли — только плейсхолдеры | реальные IP и пути к файлам паролей |

## 3. Канон и хранение: где что лежит

### 3.1. Целевая схема

| Контур | Канон | Что внутри |
|---|---|---|
| Конфигурация 1С | репозиторий **`azxasd69/perftest`** | `src\`, `ext\`, `tools\`, `docs\`, README, CHANGELOG |
| Серверная часть | репозиторий **`azxasd69/perfd`** | Go-код, `deploy\`, `docs\` (КПР, ТЗ web-контура, сверки) |
| Эксплуатация контура | **приватный** репозиторий или папка `ops\` вне публичных | журнал работ, план переноса, ревизия 1С-раздела, состояние сервера |
| Рабочая площадка | рабочая копия проекта | только то, что не документ: база, бэкапы, скрипты прогонов |

### 3.2. Решение о рабочей копии (нужно подтверждение владельца)

Сейчас `1c\perf-test` в проекте — **копия**, и она уже разошлась с репозиторием. Варианты:

| Вариант | Как выглядит | Плюсы | Минусы |
|---|---|---|---|
| **A (рекомендую)** | `1c\perf-test` становится **клоном** репозитория `perftest` (внутри свой `.git`), файлы выводятся из индекса проекта Default | одна копия, привычные пути и команды сохраняются, публикация = `git push`, разойтись физически не может | нужно один раз поправить `AGENTS.md` (пути к `tools\`), в истории Default останутся старые копии |
| B | канон — рабочая копия, публикация скриптом `tools\publish-docs.ps1` | ничего не переезжает | санитизация и структурная правка повторяются при каждой публикации, расхождение вернётся |
| C | рабочая копия — песочница, репозиторий — канон, синхронизация вручную | гибко | руками это уже проверено: 8 из 10 документов разошлись |

Вариант A: делается так — `git clone` репозитория в `1c\perf-test.new`, сравнение, переключение,
`git rm -r --cached 1c/perf-test` в Default, строка `1c/perf-test/` в `.gitignore` проекта,
правка `AGENTS.md` и `1c\README.md`. Откат — вернуть папку из истории Default одним коммитом.

### 3.3. Где живут «контурные» документы

`tools\vps\` — 7 документов на 222 КБ (журнал работ, планы переноса, ревизия, сверка, README).
Они содержат адреса, состояние сервера и решения по доступам → **публичными быть не должны**.
Предложение: отдельная папка `ops\` (вне репозиториев) либо приватный репозиторий `perftest-ops`
с санитизированной публичной выжимкой в `docs\` (только архитектура, без адресов).

## 4. Целевая структура

```
perftest/
├─ README.md                 вход: что это, требования, старт, ссылки на всё остальное
├─ CHANGELOG.md              единственная история изменений (по версиям)
├─ CONTRIBUTING.md           регламент: как менять код и документы, какие гейты обязательны
├─ SECURITY.md               как сообщать об уязвимостях, политика секретов и токенов
├─ docs/
│  ├─ README.md              ИНДЕКС: тип, вопрос, статус, версия, куда идти
│  ├─ spec/                  что требуется
│  │   ├─ ТЗ.md, ТЗ_доработка_интеграция.md
│  ├─ design/                как сделано и почему
│  │   ├─ Реализация.md, Обмен_реализация.md, Паспорт_стенда.md
│  ├─ verify/                чем подтверждено
│  │   ├─ Проверки.md, EDT_прогон.md, EDT-проверка-обмена.md
│  ├─ data/                  НОВОЕ: схема данных (регистры, измерения, реквизиты, связи)
│  ├─ ops/                   НОВОЕ: runbook — досылка, очистка, диагностика, журнал ошибок
│  ├─ decisions/             НОВОЕ: ADR — почему принято именно так
│  ├─ glossary.md            НОВОЕ: словарь (паспорт, конверт, канал, спул, уровень A/B/C)
│  ├─ refs/                  прототипы, референсы экранов, варианты логотипа, скриншоты
│  └─ archive/               заморожено: аудиты, сверки, заметки по дизайну
└─ tools/                    скрипты + их краткие README рядом
```

Правила раскладки:

- **`spec` vs `design`**: в `spec` — «должно быть» (меняется только по решению заказчика,
  версионируется как документ), в `design` — «сделано так» (меняется вместе с кодом).
- **`verify`** — только факты проверок с датами и маркерами; новые прогоны добавляют строку в
  реестр, а не раздел в конец.
- **`archive`** — документ получает статус «архив» и больше не правится; если нужен снова —
  из него делается новый документ в `spec`/`design`.
- **`refs`** — всё, что не текст: HTML-прототипы, скриншоты, превью логотипа.
- **`ops`** — эксплуатация; при публичном репозитории проходит санитизацию.

## 5. Шаблоны

### 5.1. Шапка документа (обязательна, проверяется CI)

```
| | |
|---|---|
| Документ | `Реализация.md` |
| Тип | design (как сделано) |
| Статус | актуален / отстаёт / архив / черновик |
| Проверено на версии | 1.42 |
| Дата ревизии | 10.11.2026 |
| Отвечает на вопрос | как устроены модули, формы и HTML-слой |
| Смежные документы | spec/ТЗ.md, verify/Проверки.md |
```

Правила полей:

- **Проверено на версии** — версия конфигурации, на которой документ сверяли с кодом.
  Не «когда написан». Если отстаёт — статус `отстаёт` и в шапке `отстаёт на N версий`.
- **Статус** — ровно четыре значения, без синонимов. `актуален` ставится только после сверки.
- **Отвечает на вопрос** — одна строка; если не получается — документ делится.

### 5.2. Шаблон ADR (`docs\decisions\adr-0001-....md`)

```
# ADR-0001. Тема решения
Статус: принято (10.11.2026) · Заменяет: — · Заменено: —
## Контекст     — что заставило решать, какие ограничения
## Решение      — что именно решили, одной фразой
## Альтернативы — что рассматривали и почему отклонили
## Следствия    — что теперь нельзя, что придётся поддерживать
```

### 5.3. Шаблон записи проверки (в `verify/Проверки.md`)

Одна строка реестра: `дата · версия конфигурации · что проверено · чем (команда) · результат ·
маркер/артефакт · кто`. Подробности — только если есть что разбирать, отдельным разделом
**с датой, но без даты в заголовке** (дата в шапке реестра).

## 6. Регламент ведения

### 6.1. Роли

| Роль | Что делает |
|---|---|
| Владелец | принимает решения по `spec`, ADR и публичности; утверждает релиз |
| Исполнитель (я) | правит `design`, `verify`, `data`, `ops`, CHANGELOG; держит гейты зелёными |
| Читатель | находит всё через `docs\README.md`; если не нашёл — это дефект индекса |

### 6.2. Ритм

| Событие | Обязательные действия с документацией |
|---|---|
| Любая правка поведения в коде | строка в `CHANGELOG.md` + правка тела затронутого документа (не новый раздел) + шапка: дата ревизии |
| Новая версия (`<Version>` в XML) | `CHANGELOG` новая секция; `check-version` зелёный; шапки обновлены там, где сверяли |
| Тег/релиз | чек-лист релиза (§6.4) |
| Раз в 10 версий | «день документации»: перечитать `Реализация.md`, `Обмен_реализация.md`, `Паспорт_стенда.md`, обновить шапки, слить накопленные датированные разделы в тело |
| Раз в квартал | ревизия `archive`: что пора удалить, что вернуть в работу |

### 6.3. Правила коммита документации

- Один коммит — один смысл: `docs:`, `docs(spec):`, `docs(design):`, `docs(verify):`.
- Правка кода и правка документации, описывающей это поведение, — **в одном PR/коммите**.
- Переименование файла — отдельным коммитом (`git mv`), чтобы история не рвалась.
- В сообщении — почему, а не что (что видно в диффе).

### 6.4. Чек-лист релиза

1. `python tools\check-version.py` — версия совпадает (выгрузка = README = CHANGELOG).
2. `python tools\check-links.py` — ссылки живые.
3. `python tools\check-doc-index.py` — каждый документ есть в индексе, каждый в индексе существует.
4. `python tools\check-doc-headers.py` — шапки валидны, статусы из допустимых.
5. `docs\README.md` — строка про изменённые документы (дата, версия).
6. `CHANGELOG.md` — секция версии заполнена.
7. Ручные гейты 1С (загрузка, смоук, автопрогон) — результаты в `verify\Проверки.md`.

## 7. Актуализация

### 7.1. Статусная модель

| Статус | Значение | Как попасть |
|---|---|---|
| `черновик` | пишется, читать нельзя как истину | создан вручную |
| `актуален` | сверен с кодом на указанной версии | после сверки + зелёных гейтов |
| `отстаёт` | код ушёл вперёд, документ не сверен | автоматически: `проверено на` < текущей версии |
| `архив` | не поддерживается, оставлен для истории | по решению, переносится в `archive/` |

### 7.2. Машина проверяет, человек решает

- `check-version` — уже есть: расхождение версии валит CI.
- `check-doc-headers` (новый) — шапка есть, поля заполнены, статус из списка, `Проверено на`
  равно текущей версии **или** статус `отстаёт`/`архив`. Иначе — падение.
- `check-doc-index` (новый) — документ вне индекса или битая запись индекса → падение.
- `check-links` — уже есть.
- Отдельно, предупреждением (не падением): документ не менялся дольше 30 дней при том, что
  код менялся, — кандидат на сверку.

### 7.3. Что делать с накопленными датированными разделами

В `Проверки.md` 14 разделов вида «## Тема (дата, версия)», в `Реализация.md` — 3. Порядок
работы: раздел читается, его **актуальные** факты переезжают в тело соответствующего документа,
историческая часть — в `CHANGELOG` или `archive`. Заголовок без даты остаётся один.
Это самая объёмная ручная работа плана (§10, этап 4).

## 12. Риски и что мы сознательно не делаем

| Риск | Как снимаем |
|---|---|
| Миграция канона ломает привычные пути и скрипты | этап 1 отдельным коммитом, `AGENTS.md` правится сразу, откат — один `git checkout` |
| Чистка `scratch` уничтожит уникальные замеры | перед удалением выписываем числа в `verify`; zip-архив на 30 дней |
| «День документации» не будет случаться | он привязан к версии (каждые 10) и проверяется предупреждением CI |
| Санитизация забудется при следующей правке | документы правятся только в клоне репозитория (вариант A), а не в рабочей копии |
| Слишком строгий CI начнут обходить | жёстко падают только 4 гейта; «отставание» — предупреждение |

**Не делаем:** не переписываем документы «с нуля» и не переводим их в другой формат (Word,
wiki, отдельный сайт документации). Не создаём второй индекс и не заводим «документацию в
памяти агента» как канон: память — журнал решений, а не документ.
